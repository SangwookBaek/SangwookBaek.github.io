## TL;DR

베어메탈 서버에서 GPU 추론 워커를 돌리다 OOM이 났다. 상태를 확인해보니 **GPU 사용률은 0%인데 메모리는 임계 이상으로 잡혀 있었다.** 아무 일도 안 하면서 메모리만 붙들고 있는 상태다. 프로세스를 재시작하면 풀렸다.

처음에는 단순한 메모리 누수라고 봤다. 그래서 메모리가 어떻게 할당되어 있는지부터 조사했고, 거기서 `torch.cuda.memory_allocated()`와 `memory_reserved()`라는 서로 다른 두 카운터를 알게 됐다.

찍어보니 15.4 GB를 붙들고 있으면서 실제로 텐서가 쓰는 건 1.5 GB뿐이었다. **PyTorch 관점에서 이건 누수가 아니다.** `cudaMalloc`/`cudaFree`가 느리기 때문에 PyTorch가 의도적으로 메모리를 쥐고 있는 것이었다.

---

## 1. 사용률 0%, 메모리는 그대로

추론 워커는 태스크를 하나 처리하고 다음 태스크를 기다리는 구조다. 한 프로세스가 계속 살아 있으면서 요청을 순서대로 받는다.

OOM이 나서 GPU 상태를 봤더니 이랬다.

```
+-----------------------------------------------------------------------------+
| GPU  Name             Persistence-M | Bus-Id        Disp.A | Volatile Uncorr. ECC |
| Fan  Temp  Perf  Pwr:Usage/Cap      |         Memory-Usage | GPU-Util  Compute M. |
|=============================+======================+======================|
|   1  NVIDIA ...          On          | 00000000:.. .. Off   |                  Off |
| 30%   38C    P8    ..W /  ..W        |  16090MiB / 81559MiB |      0%      Default |
+-----------------------------------------------------------------------------+
```

`GPU-Util 0%`. 계산은 아무것도 안 하고 있다. 그런데 `16090MiB`가 잡혀 있다.

태스크가 끝난 지 한참 지난 상태였고, 시간이 더 흘러도 이 숫자는 안 내려갔다. 프로세스를 죽였다 다시 띄우면 그때야 풀렸다.

## 2. 처음 가설 — 메모리 누수

재시작으로 풀린다는 건 프로세스가 뭔가를 붙들고 있다는 뜻이다. 그래서 처음에는 전형적인 메모리 누수라고 봤다. 텐서 참조가 어딘가에 남아 있고, 그게 태스크마다 쌓이는 그림을 생각했다.

누수를 잡으려면 어디서 새는지 알아야 한다. 그런데 `nvidia-smi`는 프로세스가 드라이버한테 빌려간 총량만 보여준다. **그 안에서 무슨 일이 일어나는지는 안 보인다.** 그래서 프로세스 안쪽에서 메모리가 어떻게 할당되어 있는지부터 조사했다.

## 3. torch_allocated 와 torch_reserved

PyTorch는 자기가 관리하는 GPU 메모리에 대해 두 개의 카운터를 제공한다.

```python
torch.cuda.memory_allocated()   # 텐서에게 실제로 넘어간 양
torch.cuda.memory_reserved()    # PyTorch 가 드라이버한테 받아온 총량
```

이름이 비슷하지만 다른 값이다. 태스크 전후로 둘 다 찍어봤다.

```
task_finished  torch_allocated_mib=1534  torch_reserved_mib=15458  nvidia_smi_mib=16090
```

숫자가 벌어져 있다.

```
드라이버한테 받아온 것   15,458 MiB
텐서가 실제로 쓰는 것     1,534 MiB
────────────────────────────────────
비어 있는데 안 돌려준 것 13,924 MiB
```

`nvidia-smi`가 보여주던 16 GB의 정체가 여기서 드러난다. 대부분이 **비어 있는 메모리**였다.

## 4. 이게 누수인가

누수라면 `allocated`가 커야 한다. 텐서 참조가 안 끊겨서 못 놓는 상황이니까.

그런데 큰 쪽은 `reserved`였다. `allocated`는 전체의 10%도 안 된다. 즉 **PyTorch는 그 메모리가 비어 있다는 걸 알고 있다.** 자기 장부에 "이 자리는 재사용 가능"이라고 적혀 있는 상태다.

이건 잃어버린 메모리가 아니다. PyTorch 관점에서 누수가 아니다.

그럼 왜 안 돌려주나. 여기서 PyTorch의 메모리 전략을 보게 됐다.

## 5. cudaMalloc 이 느리다

GPU 메모리를 드라이버한테 받아오는 원시 연산은 두 개다.

```
cudaMalloc / cudaFree
```

문제는 이게 느리다는 것이다. 드라이버로 진입해서 페이지 테이블을 건드리고, 동기화까지 건다. 특히 `cudaFree`는 앞선 작업이 끝날 때까지 기다리기 때문에 CPU와 GPU가 겹쳐 도는 걸 방해한다.

딥러닝 워크로드는 텐서를 초당 수천 개씩 만들고 버린다. 여기서 매번 `cudaMalloc`을 부르면 커널 실행보다 메모리 할당에 더 오래 걸리는 상황이 나온다.

그래서 PyTorch는 **드라이버한테 큰 덩어리를 한 번 받아놓고 자기가 잘라 쓴다.** 텐서를 놓아도 드라이버로 돌려주지 않고 재사용 대기열에 넣는다. 다음 텐서는 `cudaMalloc` 없이 그 자리를 받는다.

캐싱 할당자(caching allocator)라고 부르는 이유다. **목표는 정상 상태에서 `cudaMalloc`/`cudaFree`를 한 번도 안 부르는 것이다.**

## 6. segment 와 block

이 전략이 두 카운터의 정의를 만든다.

```
Segment  = cudaMalloc 한 번으로 받아온 덩어리      → 합계가 reserved
 └ Block = 세그먼트를 잘라 텐서에게 준 조각        → allocated
```

세그먼트 안은 이렇게 생겼다.

```
Segment (20 MB, cudaMalloc 으로 받음)
┌────────┬──────────┬────────┬─────────────────┐
│ Block  │  Block   │ Block  │     Block       │
│ 쓰는중 │  비었음   │ 쓰는중 │     비었음      │
└────────┴──────────┴────────┴─────────────────┘
   ↑ 이 두 개만 allocated
   ↑ 세그먼트 전체 20 MB 는 reserved
```

`reserved − allocated`가 곧 재사용 대기열이다. 아까 본 13,924 MiB가 이것이다.

### 라이프사이클

각 카운터가 언제 움직이는지 정리하면 이렇다.

1. **텐서 생성** — 대기열에서 맞는 블록을 찾아 자른다. `allocated` 증가, **`reserved`는 그대로**
2. **맞는 블록이 없음** — `cudaMalloc`으로 새 세그먼트를 받는다. **`reserved`가 오르는 유일한 지점**
3. **텐서 해제** — 블록을 비었음으로 표시하고 양옆 이웃이 비어 있으면 합친다. `allocated` 감소, **`reserved`는 그대로**
4. **`empty_cache()`** — **통째로 비어 있는** 세그먼트만 `cudaFree`. `reserved` 감소

3번이 핵심이다. **텐서를 놓는 것만으로는 `nvidia-smi` 숫자가 안 내려간다.** 4번을 부르거나 프로세스가 죽어야 내려간다.

### 세그먼트 크기

크기가 고정은 아니고 요청에 따라 규칙이 다르다.

| 요청 크기 | 세그먼트 |
|---|---|
| 1 MB 미만 | 2 MB 고정 |
| 1 ~ 10 MB | 20 MB 고정 |
| 10 MB 초과 | 요청 크기에 맞춤 |

앞의 두 구간은 요청과 무관하게 정해진다. 512 KB 하나 달라고 해도 2 MB를 받아온다. 작은 할당이 수천 개 쏟아질 걸 알기 때문에 미리 크게 받아 잘라 쓰는 것이다.

### 블록은 세그먼트를 넘지 못한다

하나의 텐서는 **하나의 세그먼트 안에 있는 연속된 하나의 블록**이어야 한다. 예외가 없다.

반납 때문이다. `cudaFree`는 `cudaMalloc`이 돌려준 포인터 하나만 받는다. 세그먼트를 반쪽만 반납할 수도, 두 세그먼트를 한 번에 반납할 수도 없다. 그래서 블록 병합은 **같은 세그먼트 안 이웃끼리만** 일어난다. 주소가 우연히 붙어 있어도 다른 `cudaMalloc`의 결과물이면 안 합친다.

이 제약이 이런 상황을 만든다.

```
Segment A (20 MB)  [ 쓰는중 2 | 비었음 18 ]
Segment B (20 MB)  [ 쓰는중 2 | 비었음 18 ]

빈 공간 총 36 MB.   30 MB 요청 → 실패.
```

빈 메모리가 충분한데 OOM이 나는 경우가 대부분 이것이다. 파편화라고 부른다.
