[지난 글](/posts/gpu-memory-reserved-allocated-caching-allocator/)에서는 PyTorch와 CuPy가 각자 가지고 있던 메모리 풀을 RMM으로 합쳐봤다. 한쪽에서 해제한 메모리를 다른 쪽에서도 재사용할 수 있게 하려는 목적이었다. 작은 실험에서는 실제로 재사용되는 것도 확인했다.

이를 적용해 운영하면서 모니터링하던 중 이상한 일이 생겼다. 특정 모델에서 RMM을 켜기 전보다 켰을 때 VRAM을 더 많이 점유하는 문제가 생긴 것이다.

기존에는 24 GiB 아래였던 추론의 메모리 피크가 RMM을 켜자 31 GiB를 넘었다. 끄면 다시 내려간다. 메모리를 효율적으로 쓰려고 넣었는데 오히려 더 먹고 있었다.

같은 계산인데 RMM을 켰을 때 왜 메모리가 더 늘어나는 걸까. 풀에 남은 캐시인지, 계산 중에 추가로 잡히는 메모리인지부터 확인해보자.

## 정말 같은 계산인데 RMM만 켜면 늘어나나

먼저 예전에 찍은 숫자와 지금 숫자를 바로 비교하지 않기로 했다. 워커 이미지나 입력이 달라져도 피크는 달라질 수 있다. 이전 실험의 이미지와 모델 artifact, 입력을 고정하고 같은 H100 PCIe의 MIG 3g.40gb 슬롯에서 다시 실행했다.

특정 모델에 동일한 입력 하나를 넣어 비교했다. 노드 24,684개, 시간축 400,001개, 공간 배치 크기 736. 여기서 736은 요청을 736개 모았다는 뜻이 아니라, 한 번에 계산할 공간 위치의 수다. 각 위치에 긴 시간 이력이 붙으니 배치 하나도 작지 않다.

환경은 Python 3.10.20, PyTorch 2.8.0+cu126, Numba 0.61.2, CuPy 13.6.0, RMM 26.2.0이다. CPU 8개와 RAM 64 GiB 조건을 유지했고, 연산 캐시는 껐다. RMM을 켠 실행의 release threshold는 4,096 MiB였다.

| 같은 입력의 전체 실행 | VRAM 피크 | CPU RAM 피크(RSS) | 실행 시간 |
| --- | ---: | ---: | ---: |
| RMM off, 새로 실행 | 22.913 GiB | 2.201 GiB | 331.4초 |
| RMM on | 31.180 GiB | 1.865 GiB | 338.1초 |

VRAM은 NVML로 MIG 전체 사용량을 20 ms 간격으로 읽은 관측 피크다. 다른 GPU 프로세스가 없는 조건에서 측정했다. 시간에는 실행 컨텍스트 구성, 모델 계산, GPU 동기화와 결과 직렬화를 포함했고, import와 큐 대기, 최종 파일 쓰기는 제외했다.

이전에 RMM off에서 얻은 23.14 GiB도 같은 입력의 완료된 실행이다. 이번 재실행은 22.91 GiB였다. 서로 다른 실행의 피크가 완전히 같지는 않았지만, RMM on의 31.18 GiB는 분명히 컸다. 결과 14개와 노드 ID는 기존 비교 기준을 통과했다.

계산 결과는 같은데, 계산 도중 필요한 메모리만 늘어난 셈이다.

## 풀에 남겨둔 캐시가 8 GiB인 걸까

지난 글에서 봤듯이 `nvidia-smi`에 잡히는 메모리에는 살아 있는 텐서뿐 아니라 할당자가 보관하는 빈 공간도 들어간다. 그러면 이번에도 RMM이 메모리를 많이 보관하는 것 아닐까.

그래서 NVML만 보지 않고 RMM 쪽의 아직 해제되지 않은 요청 바이트와 CUDA pool의 used 카운터를 같이 봤다. **늘어난 부분은 단순히 비어 있는 reserved 공간으로 설명되지 않았다. 아직 해제되지 않은 할당이 남아 있었다.**

작게 분리한 실험에서 release threshold를 0으로 바꿔도 이 현상의 설명이 되지 않았다. 원래 전체 실행에서도 추적할 대상은 풀의 보유 정책보다, 누가 할당을 계속 붙잡고 있는지였다.

배치가 끝나면 이전 배치의 큰 텐서는 없어질 거라고 생각했다. 그런데 weak reference로 생존 여부를 확인해보니 첫 배치에서 만든 시계열 텐서가 다음 배치에서도 살아 있었다.

이 텐서 하나의 크기는 다음과 같다.

```text
736개 위치 × 400,001개 시점 × float64의 8바이트
= 2,355,205,888 bytes
≈ 2.193 GiB
```

이전 텐서 하나만 더 살아 있어도 2 GiB 이상이다. 여기서부터는 캐시를 얼마나 비우느냐보다, 이전 배치의 텐서가 왜 아직 살아 있는지가 궁금해졌다.

## del을 했는데 누가 잡고 있지

이 계산은 PyTorch만으로 끝나지 않는다. PyTorch로 만든 시계열 배열을 Numba CUDA 커널에 넘겨 후속 계산을 수행한다. 이때 `cuda.as_cuda_array()`로 Numba가 볼 수 있는 배열을 만든다.

Numba의 이 변환은 데이터를 복사하지 않는 view를 만들고, 원본 객체에 대한 참조를 유지한다. view를 쓰는 동안 원본 메모리가 사라지면 안 되기 때문이다. [Numba의 CUDA Array Interface와 객체 수명 설명](https://numba.readthedocs.io/en/stable/cuda/cuda_array_interface.html#lifetime-management)

그러면 원본 텐서의 변수 이름을 지워도 Numba 쪽 view가 남아 있으면 저장 공간은 그대로일 수 있다. 그런데 실제 코드에서는 view와 텐서 둘 다 배치 끝에서 `del`하고 있었다.

참조를 더 따라가니 이런 경로가 나왔다.

```text
Numba 컴파일러 frame
  → dispatcher에 전달한 args tuple
    → DeviceNDArray
      → MemoryPointer._owner
        → 첫 배치의 PyTorch 시계열 텐서
```

배열을 사용하는 계산 루프의 이름은 지웠는데, **처음 커널을 JIT 컴파일하던 쪽의 frame에서 배열로 이어지는 참조가 남아 있었다.**

여기서 frame은 함수 실행 중 지역 변수와 호출 관계를 가지고 있는 Python 객체다. 함수가 반환했다고 해서, 그 frame을 가리키는 참조까지 반드시 없어진 것은 아니다.

실제로 첫 번째 계산 함수가 반환한 뒤에도 그 함수의 frame과 지역 배열들이 남아 있었다. 첫 시계열만 남은 게 아니라 계산용 workspace 세 개도 같이 잡혀 있었다.

| 남아 있던 배열 | 크기(bytes) |
| --- | ---: |
| 첫 배치 시계열 | 2,355,205,888 |
| 같은 크기의 workspace 3개 | 7,065,617,664 |
| 공간 입력 배열 3개 | 5,924,160 |
| 시간축 입력 배열 | 32,000,080 |
| 결과 buffer와 lookup 배열들 | 12,032 |
| 합계 | **9,458,759,824** |

합치면 약 **8.809 GiB**다.

이 숫자가 흥미로웠다. 같은 지점에서 명시적으로 GC를 실행하자 RMM의 미해제 요청 바이트가 19,063,247,483에서 9,604,487,659로 줄었다. 차이가 정확히 **9,458,759,824 bytes**였다. 추적한 배열의 합과 회수된 양이 맞았다.

NVML 피크끼리 빼면 allocator의 예약 공간과 측정 시점까지 섞인다. 여기서는 같은 카운터에서 줄어든 요청 바이트와 남아 있던 배열의 실제 크기를 비교했다. 그래서 단순히 “GC를 하니 좀 줄었다”보다 구체적으로 어디가 줄었는지 말할 수 있었다.

## Python GC가 GPU 메모리를 줄인다고?

처음에는 GPU 메모리 문제인데 Python GC가 해결한다는 게 좀 이상했다.

내가 이해한 흐름은 이렇다. Python GC가 GPU의 빈 영역을 직접 찾아 정리하는 것은 아니다. GPU 배열을 소유한 Python 객체가 회수되면, 그 객체가 쥐고 있던 GPU 메모리도 할당자에 해제될 수 있다.

```text
Python 참조 정리
  → Numba view와 원본 텐서의 수명 종료
    → GPU 할당 해제
      → 할당자가 재사용하거나 CUDA에 반납
```

CPython에는 참조 횟수에 따른 회수와 순환 참조를 찾는 GC가 함께 있다. `del`은 그 이름의 참조를 제거한다. 다른 경로나 순환 구조가 객체를 붙잡고 있으면 그것만으로 객체가 회수되지는 않는다. [Python 3.10 GC 문서](https://docs.python.org/3.10/library/gc.html)

이번에는 명시적인 `gc.collect()` 뒤에 이전 텐서의 weak reference가 사라지고, 해당 크기의 할당이 해제되는 것을 같이 봤다. Numba 컴파일러와 type inference frame까지 이어지는 경로도 확인했다.

다만 **순환을 닫는 마지막 참조가 정확히 어느 예외 객체에서 만들어졌는지까지 확정한 것은 아니다.** type inference 내부에서 임시 예외를 다루는 코드가 후보였지만, 여기부터는 확인한 경로와 가설을 구분해야 한다.

반대 방향도 확인했다. RMM을 끈 상태에서 자동 GC를 비활성화하니, 36개 배치를 관찰한 짧은 실험에서도 피크가 31.69 GiB까지 올라갔다. 이 실행은 관찰 지점에서 일부러 멈췄고 전체 추론을 완료한 결과는 아니다. 그래도 RMM이 없어도 참조 회수가 늦어지면 비슷한 메모리 증가가 생길 수 있다는 근거는 됐다.

## 그런데 왜 RMM을 켰을 때만 보였을까

여기까지로는 설명이 덜 됐다. 참조가 남는 곳은 Numba인데, 왜 RMM on/off가 그렇게 뚜렷하게 갈렸을까.

RMM 활성화 과정을 나눠봤다. 라이브러리 import, pool 객체 생성, PyTorch allocator 교체, cuDSS hook 연결을 분리해서 비교했다. cuDSS hook을 빼도 첫 배치 이력은 계속 남았다.

그러다 더 이상한 결과가 나왔다. 원래 RMM off로 실행하던 스크립트에 **`import cupy`, 그다음 `import rmm`만 추가해도** 첫 배치 이력이 남았다. pool 객체를 만들거나 GPU allocator를 RMM으로 바꾸지 않은 상태였다.

아래는 각각 새 프로세스에서 첫 6개 배치까지만 실행한 비교다. 전체 추론 피크와는 별도다.

| 실행 조건 | 배치별 살아 있는 시계열 개수 | 6개 배치 관측 피크 |
| --- | --- | ---: |
| 원래 native allocator 실행 | 1, 1, 1, 1, 1, 1 | 22.913 GiB |
| native + RMM만 import | 1, 1, 1, 1, 1, 1 | 22.913 GiB |
| native + CuPy, RMM 순서로 import | 1, 2, 2, 2, 2, 2 | 24.626 GiB |
| RMM allocator 활성화 | 1, 2, 2, 2, 2, 2 | 24.555 GiB |

이 결과 때문에 “RMM allocator가 메모리를 더 할당해서 생겼다”는 설명을 그대로 유지할 수 없었다. allocator를 바꾸지 않아도 같은 참조 잔류가 생겼으니까.

GC callback을 붙여보면 첫 Numba 컴파일 과정의 수집 시점도 달랐다. Python 3.10의 자동 GC는 객체의 할당·해제 횟수와 세대 상태를 기준으로 실행된다. import가 앞에서 만드는 Python 객체들도 이 상태에 영향을 줄 수 있다. [Python 3.10의 GC threshold 설명](https://docs.python.org/3.10/library/gc.html#gc.set_threshold)

현재는 **RMM을 켜는 준비 과정이 Python 객체와 GC의 진행 상태를 바꾸면서, 첫 JIT 컴파일에 연결된 참조가 오래 남는 문제가 드러났다**고 보고 있다. 어떤 개별 객체 할당이 어느 임계값을 넘겼는지까지 분리한 것은 아니다. import 두 개의 순서를 뒤집는 실험도 하지 않았다.

그래서 import 순서만 바꿔서 고쳤다고 하기는 어렵다. 다른 라이브러리가 추가되거나 초기화 과정이 달라지면 GC 타이밍도 다시 달라질 수 있다. 고칠 대상은 우연히 수집이 빨리 일어나게 만드는 순서보다, 큰 배열이 불필요하게 오래 살아 있는 구간에 가까워 보인다.

## 그러면 RMM을 유지해도 내려가나

이제 원래 질문으로 돌아왔다. RMM을 끄는 대신 참조 회수를 명시적으로 하면 어떨까.

진단용 실행에서 Numba 배치의 동기화 뒤마다 GC를 호출하고, 같은 입력의 전체 추론을 끝까지 돌렸다. 모델 artifact는 그대로 두고 실행 harness에서 회수 시점을 추가했다.

| 같은 입력의 전체 실행 | VRAM 피크 | CPU RAM 피크(RSS) | 실행 시간 |
| --- | ---: | ---: | ---: |
| RMM off | 22.913 GiB | 2.201 GiB | 331.4초 |
| RMM on | 31.180 GiB | 1.865 GiB | 338.1초 |
| RMM on + 배치마다 GC | **22.368 GiB** | **1.870 GiB** | **352.4초** |

RMM을 유지해도 피크가 약 8.81 GiB 내려갔다. 출력 14개는 기존 허용오차인 `rtol=1e-6`, `atol=1e-8`을 통과했고 노드 ID도 일치했다. byte 단위로 동일하다는 의미는 아니다.

시간은 기존 RMM on보다 약 14.3초, **4.2% 늘었다.** RMM off와 비교하면 약 6.3% 느리다. 각 조건의 개별 실행 결과이므로 이 비율을 반복 측정한 평균 성능으로 보지는 않는다.

메모리를 낮추는 방향은 확인했지만, 배치마다 GC를 하는 것이 최종 구현이어야 하는지는 남아 있다. 첫 JIT 컴파일 뒤에 한 번만 회수해도 되는지, 새 signature가 컴파일될 때마다 필요한지, 작은 입력으로 미리 컴파일하는 편이 나은지는 별도로 확인해야 한다. 추론 전에 이미 GC를 한 번 하는 코드가 있었지만, 그 뒤 첫 컴파일에서 생기는 참조에는 충분하지 않았다.

그리고 이 결과는 고정한 H100 환경에서 특정 모델의 입력 하나를 검증한 결과다. 22.37 GiB라는 숫자만 보고 24 GB L4에서도 안전하다고 결론 내릴 수는 없다. 그쪽에서 확인한 CUDA 사용 가능 용량은 약 22.04 GiB였고, 실행 환경도 다르다.

이번에는 RMM을 켰다는 설정값을 보고 RMM의 메모리 보유 정책부터 의심했다. 따라가 보니 GPU 배열의 수명을 Python 컴파일러 frame이 늘리고 있었다. 풀을 합쳐 재사용하는 문제 앞에, 그 배열을 재사용 가능한 상태로 돌려놓는 문제가 있었던 셈이다.

지금은 RMM을 유지하면서 이 입력의 피크를 낮출 수 있다는 데까지 확인했다. 실제 코드에 넣을 최소한의 회수 위치는 아직 정하지 않았다. 다음에 보고 싶은 것은 GC를 많이 호출하는 방법보다, 첫 컴파일이 끝났을 때 무엇이 남아 있고 정확히 언제 한 번 정리하면 충분한가다.
